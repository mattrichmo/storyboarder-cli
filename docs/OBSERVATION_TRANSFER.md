# Observation plan transfer

Observation plans can move between copies of the same Storyboarder project. A transfer keeps contract IDs, shot IDs, every immutable version, operation and timestamp, canonical body and basis hashes, and each exact source and reference pin. The plan does not contain artifact filesystem paths or copy screenplay artifacts; the target project must already contain the matching project records and artifact hashes.

The application interface is `export_observation_plan(service)`, `preview_observation_import(service, plan, choices=None)`, and `apply_observation_import(service, plan, preview)`. The shared command catalog exposes `observation.plan-export`, `observation.plan-import-preview`, and `observation.plan-import-apply` to both the CLI and JSON API. They are API-safe JSON operations and remain outside the browser command catalog; no command accepts a project path or writes an exported file. Export returns deterministic UTF-8 JSON using the `storyboarder.observation-plan/v1` schema. Its manifest hashes the canonical plan payload and every complete version record, including the stored content and basis hashes.

Use `observation.plan-export` with an empty payload. It returns a command result whose `plan` property contains the portable plan. Save that complete CLI JSON result as `export.json`; its wrapper is already the `plan` field expected by `observation.plan-import-preview`, so pass it directly as `--payload @export.json`. The API sends `{"plan": <exported result's plan>}` as its preview request body. Apply uses `plan` plus the unchanged `preview` receipt in one command payload.

`observation.plan-import-preview` also accepts optional `choices`, a map from each conflicting contract ID to `skip-conflict` or `abort`. Save the complete preview receipt and pass it with the unchanged plan to `observation.plan-import-apply`. A 409 `observation_transfer_target_changed` means target data changed after preview; obtain a fresh preview before applying. The application accepts plans up to 48 MiB. CLI file payloads can use that limit; the generic JSON API request body is capped at 2 MiB, including the plan and preview JSON, and returns 413 `too_large` above that transport limit.

Import is a dry-run first. Preview opens the project read-only, reports exact-ID conflicts and basis versions that would be stale, and returns a receipt bound to the plan manifest, reconciliation choices, and digest of the complete logical target database. If target state changes, apply returns `observation_transfer_target_changed`; run preview again before applying. Apply rechecks the digest under a single transaction and restores the original history rows through the short-lived trusted restoration gate. It does not generate replacement IDs, retarget pins, or rewrite historical operations. Identical re-imports are reported as already present and do not advance revisions or add events.

Every conflicting contract needs an explicit `skip-conflict` or `abort` choice in a new preview. Skipped conflicts are listed as losses and unresolved items. Missing or mismatched source edges, node identities, hashes, and reference identities are not matched by title, position, or latest version. A plan with absolute paths, credentials, or runtime-launch fields is rejected with an `adapter_losses` report instead of being sanitized, so saved canonical history remains intact.
